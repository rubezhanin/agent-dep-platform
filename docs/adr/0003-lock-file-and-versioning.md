# ADR-0003: Lock File and Versioning

- **Status**: Accepted
- **Date**: 2026-08-31
- **Supersedes**: TZ §9 (Lock file) and §15 (Dependency resolution) by
  fixing the contract for MVP and the 1.x extension path.

## Context and Problem Statement

The TZ §9 specifies `agency.lock`:

```yaml
lockVersion: 1
source:
  repository: git@github.com:company/agents.git
  commit: abc123...
agents:
  backend-architect: 2.4.0
skills:
  postgres: 3.1.0
renderers:
  hermes-router: 1.0.0
```

And TZ §15.1 says MVP uses exact versions only; SemVer ranges and a
solver are deferred to 1.x.

This ADR fixes:

- The lock file's role in deployment reproducibility (TZ §1.1.4
  "deployment must be reproducible from a known immutable snapshot").
- The resolver's MVP behavior (exact-version only) and the 1.x
  extension path.
- Conflict diagnostics (TZ §15.2 "diamond dependency" handling).
- Lock file regeneration semantics — when the lock is updated, when
  it is not.

## Decision

### Lock file is the source of truth for production deploys

Per TZ §1.1.4 and §9, production deploys (`agency deploy <system>`)
**must** be run against a system definition that references a lock
file. A "head-of-source" deploy is allowed in dev only and surfaces
as `WARN: lock not used` in the plan UI.

The lock file is:

- **Authoritative** for versions: every agent and skill in the system
  must resolve to the version listed in the lock. No exceptions, no
  "I'll just use whatever is in source."
- **Immutable per commit**: the lock is bound to a specific source
  commit. Editing the lock implies a new commit; the deploy is then
  reproducible from that new commit.
- **Stored as YAML in the system repository** (not in our app's local
  state) so it travels with the system definition and is reviewable
  in PRs.

### MVP resolver: exact versions only

For each `agent` and `skill` reference in `system.yaml`, the resolver
must find a single exact-version match in the source snapshot. If
multiple versions exist for the same `id` and a `system.yaml`
references it without a version, that is a hard error (resolution
ambiguity). If the referenced version is not in the snapshot, that
is also a hard error (resolution failure).

No SemVer ranges, no floating versions, no "latest", no "compatible
with". MVP rule: the lock file is the resolution; no lock, no
production deploy.

### Lock file regeneration is explicit

The lock is regenerated by `agency lock <system>`, which:
- Reads the current `system.yaml`.
- Reads the frozen source commit from the resolved snapshot.
- Emits `agency.lock` with the exact versions used.

It is **not** regenerated as a side effect of `agency deploy`.
`deploy` reads the lock; if the lock is missing or stale (source
commit does not match the current snapshot), `deploy` errors out
with a clear "lock stale; run `agency lock <system>` to refresh"
message.

### Conflict diagnostics

The TZ §15.2 example:

```text
A → skill X 2.0
B → skill X 2.5
```

is reported as a hard error in MVP:

```
ERROR: dependency conflict
  backend-architect (2.4.0) requires postgres 2.0
  database-engineer (1.3.0) requires postgres 2.5
  no compatible version satisfies both
fix: pin the shared skill in agency.lock to a single version, or
     remove one of the agents from the system definition
```

The error names the agents, the conflicting versions, and the fix.
No automatic resolution; the user must edit `system.yaml` or
`agency.lock` and re-run.

### Skill-version uniqueness within a system

A single `system.yaml` cannot reference the same `skill` id at two
different versions, even transitively. The lock file
canonicalization step in `agency lock` fails if it detects this
condition.

### Renderer pinning

The TZ §9 example lists `renderers: hermes-router: 1.0.0`. The
renderer is a hermes-side artifact; in MVP the renderer version is
recorded in the lock but the rendered artifact is hashed and stored
in the CAS (TZ §11.2). At deploy time, the app renders once from
the current source + lock and verifies the resulting hashes match
the deployment record. If they don't, the deploy is rejected as
"renderer version mismatch" (re-render required, do not auto-update
in production).

### 1.x extension (informational, not implemented in MVP)

When 1.x adds SemVer ranges, the lock file format extends with a
`resolver: { mode: exact | semver }` field. The default remains
`exact`; opting into `semver` requires explicit policy and per-system
configuration. Diamond-dependency conflicts in `semver` mode get
the same hard error (no auto-resolve); the difference is the
*eligible* version set.

## Consequences

### Positive

- Production deploys are byte-identical reproducible: same lock +
  same source commit + same renderer version → same CAS content.
- Plan UI can diff two locks (current vs new) and show the user
  exactly what changes; this is the core of "Plan before Apply"
  (TZ §1.1.6, §16).
- The lock is human-reviewable as a regular PR; version changes are
  never silent.

### Negative

- "Latest" workflows are unsupported; users must always re-lock
  before deploying. This is intentional but adds friction for fast-iterating
  teams.
- Diamond-dependency conflicts are hard errors; users must hand-edit
  `system.yaml`. A future "auto-pick highest within the constraint set"
  mode could ease this but is not in MVP or 1.x.
- Lock regeneration requires reading the full source; for very large
  catalogs this is the slowest step in the pipeline. We accept this.

### Neutral

- The lock format is intentionally small (TZ §9). We will not add
  fields speculatively. 1.x additions are opt-in and versioned via
  `lockVersion`.
- The lock is per-system, not global. Two systems in the same
  workspace can have different locks.

## Alternatives considered

1. **Allow "floating" versions (`postgres@^3`) with a solver.**
   - Rejected for MVP (TZ §15.1). Adding it later (1.x) requires no
     breaking change to the lock format thanks to `lockVersion`.

2. **Auto-regenerate the lock on every deploy.**
   - Rejected. This would let a deploy silently pick up new upstream
     versions, breaking reproducibility and the audit trail. The
     explicit `agency lock` step is a feature, not a wart.

3. **Global lock across all systems in a workspace.**
   - Rejected. Different systems legitimately want different versions
     of the same skill (e.g., `system-a` wants `postgres@2` for
     legacy, `system-b` wants `postgres@3` for new work). Per-system
     lock is the right unit.

4. **Cargo-style `[patch]` / `[replace]` overrides in the lock.**
   - Rejected for MVP. Adds complexity for a use case (overriding
     upstream versions) that we can serve in 1.x if it materializes.
